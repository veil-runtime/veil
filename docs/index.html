Governed execution, with or without AI

A safer way for software and AI to act on your systems.

Decide which operations your application makes available, check requests against your rules, and see what happened.

Veil is a reusable execution boundary for existing software, human workflows and AI-assisted tools. Your application supplies the operations and policy; Veil governs their execution.

An example integration

A request is a starting point. Permission comes next.

A service assistant proposes updating a customer record. Your application decides which record, fields and caller are permitted before the operation runs.

  • Check the request. Is the operation registered, and is its declared input valid?
  • Apply your policy. Does your application allow this caller to make this change?
  • Inspect the outcome. See whether the operation completed, failed or was denied.

Illustrative application pattern, not a deployed customer service or a built-in customer-record integration.

The problem

Knowing what to do does not establish permission to do it.

Software and AI can request useful work. Connecting those requests directly to business systems leaves each integration to handle input checks, permissions and reporting on its own. A plausible request can still target the wrong record or ask for an action your organisation has not approved.

01 / Intent

Requests need boundaries

A workflow, person or model can propose an action. That proposal must still pass the rules of the system performing it.

02 / Policy

Rules need a place to run

Checks scattered across scripts and tool calls are harder to review consistently. A shared execution path gives policy a defined place.

03 / Outcomes

Activity needs explanation

A generated answer is not evidence that an operation succeeded. Teams need the execution status, results and events.

The governed execution layer

One boundary between a request and the work it asks for.

Veil receives a structured request, checks it, asks your application's authorization policy, and invokes registered operations. The same execution contracts work whether the request comes from deterministic software, a human workflow or an optional planner.

Make approved work reusable

Wrap an existing API call, calculation or operational task as a named operation, called a capability. Declare its inputs and risk, then register it with the runtime. Different workflows can request the same operation through the same governed path.

Understand capabilities

Keep authority with your application

Your trusted application supplies caller information and the rules that allow or deny work. By default, Core permits read operations and denies write and destructive operations. An AI proposal grants no additional permission.

Understand authorization and its limits

Core does not require an AI model or own the intelligence behind a request. It is not a general autonomous agent, an identity-management replacement, a compliance certification or a replacement for your enterprise applications.

How it works

Request → Validate → Authorize → Execute → Record.

These are the stages of the governed path. Veil checks a plan before creating a job, then resolves, validates and authorizes each step before invoking its capability.

  1. Request

    Your application submits a structured plan describing the registered work it wants done.

  2. Validate

    Check operations, supplied versions and declared inputs. Resolve earlier results and validate each step's input.

  3. Authorize

    Your configured policy allows or denies the operation using its resolved input and trusted caller context.

  4. Execute

    Invoke the allowed capability. Its application-owned implementation interacts with the relevant system.

  5. Record

    Return job outcomes and lifecycle events. Your host chooses storage, retention and access to that evidence.

Events are emitted throughout execution; “Record” summarises the observable outcome, not a separate compliance audit service. Read the full execution lifecycle.

Business value

Control how connected work gets done.

A reusable execution boundary gives teams a common place to define available operations, apply their rules and inspect results. Its value depends on the capabilities and policies your application implements.

Control

Make specific operations available and decide which requests may invoke them. Registration alone is not permission.

Consistency

Route different request sources through the same validation, authorization and execution lifecycle.

Reuse

Offer a reviewed integration to several workflows without giving each planner direct integration authority.

Traceability

Connect a plan to its job, step events and results. Configure the host's storage and retention to fit your needs.

Incremental modernisation

Wrap a bounded operation in an existing system. Evaluate one workflow before expanding the integration.

Practical applications

Start with a specific action and a clear owner.

The following are possible application patterns, not production deployments or ready-made connectors. Your application provides integrations, authenticated caller context, authorization and any review interface.

AI-assisted service workflows

Let an assistant propose a record lookup or update. Validate the requested operation and apply your policy before touching the service system.

Enterprise process automation

Read an order, check its status and request a permitted follow-up in ordered steps. Keep the execution result separate from the workflow's description.

Legacy modernisation

Expose one approved operation around an existing application or API. Add a new request source while keeping the existing system in place.

Reusable integrations

Package a reviewed set of operations for several internal workflows. Each request still goes through authorization.

Developer and operational tooling

Wrap a status check or staging operation as a capability. Allow it only for the caller and target your host policy permits.

Human-approved actions

Use your application's approval process to establish a trusted decision. Its authorizer checks that decision before allowing the requested action.

Demonstrated in repository examples: a deterministic echo, dependent plan steps and a policy that denies unauthorized production actions. Human approval is an application integration pattern; Core does not ship an approval inbox or approval workflow. Explore the deterministic example and production-denial example.

Architecture and ecosystem

Separate the decision from the authority to act.

Reasoning and planning are modular inputs. Core receives plans and governs execution. Interfaces and experimental autonomous behaviour have their own product boundaries.

Core

Governed execution

The runtime, capability and authorization model, plans, jobs and events. Independently usable without a model, UI or autonomous loop.

UI / independent

System-described interfaces

Independently developed interfaces that describe and expose system interactions. UI is not included in the Core v0.4.0 package.

Emergence / experimental

Reasoning and coordination

Experimental coordination and autonomous behaviour, moving into its own package. Emergence is not included in Core v0.4.0.

Technical model: how Core connects intent to systems

ExecutionPlan is the boundary between reasoning and execution. OperatorRuntime governs execution. Capabilities define work; application-owned providers interact with external systems.

In the internal planning path, planners reason, strategies orchestrate and PlannerRouter selects strategies. Applications can submit plans directly without using that path.

V1 runs ordered steps by default. V2 is host opt-in. Default authorization allows read-risk capabilities and denies write/destructive ones. Identity verification, correct risk labels, credentials and external side effects remain host responsibilities.
