# Veil v0.3.0

**Release candidate documentation.** This page describes the prepared v0.3.0
candidate relative to published v0.2.0. It is not a publication announcement;
the npm registry continues to serve v0.2.0 until the authorized release process
is complete.

## Shipped candidate functionality

### ExecutionPlan versions and admission

- ExecutionPlan `2.0` adds ADR-0011 governed receiving-value semantics. It is
  available only when trusted host configuration includes `2.0` in
  `OperatorRuntimeOptions.planVersions`.
- Omitting `planVersions` remains equivalent to `['1.0']`. A host can explicitly
  support both versions with `['1.0', '2.0']`; there is no automatic upgrade,
  downgrade, negotiation or stored-Job migration.
- Every submitted plan version is admitted before Job creation. Missing,
  malformed, unsupported and host-disabled versions reject without
  authorization or capability invocation.
- Structured admission diagnostics expose stable issue codes through the
  root-exported `isPlanAdmissionError` predicate and public diagnostic types.
  The issuer and containment machinery remain private.

### Governed receiving values

For an admitted V2 step, Veil resolves references, captures the receiving value,
validates the capture, presents a detached recursively frozen authorization
copy, requires explicit allow, constructs a detached mutable capability copy,
and only then transitions to running/`capability.started` and enters the
capability. Unsupported V2 representations fail closed rather than falling back
to V1.

V1 retains its historical receiving-value identity and mutation behavior. The
same runtime can admit V1 and V2 when the trusted host explicitly chooses mixed
admission. See [ExecutionPlan V2](../reference/execution-plan-v2.html) and the
[V1 to V2 migration guide](../guides/migrate-to-execution-plan-v2.html).

### References, authorization and entry hardening

- ADR-0013 gives V1 and V2 the same exact result-reference recognition rule: an
  object must have exactly one own key, `$ref`, as an enumerable data property
  containing a primitive string.
- The repository's generic execution, jobs and LinkedIn routes enter through
  `OperatorRuntime` with caller identity supplied only by trusted host
  configuration. Request or plan fields such as `approved`, `caller`, `scopes`
  and `risk` do not supply authority.
- `POST /api/jobs/:id/execute` is retired with unconditional `410`. Clients must
  submit a new plan through the governed runtime path.
- Authorization failures, malformed decisions and route/admission failures stop
  before capability work. Public route responses do not expose private
  admission evidence.
- `http.request` now conservatively declares destructive risk for its combined
  method surface, so the default authorizer denies it. Shell execution uses
  destructive risk and exact reviewed executable/argv tuples rather than prefix
  matching.

The routes and built-in HTTP/shell capabilities are repository/server surfaces,
not new npm root exports. Their hardening is still user-visible to applications
running the bundled server or those repository integrations.

## Compatibility and migration from v0.2.0

v0.3.0 is a pre-1.0 minor release with new functionality and deliberate
contract tightening. Existing consumers should review these changes:

- **`plan.version` is enforced at runtime.** Supply exact `version: '1.0'` for
  existing plans. Do not rely on missing, malformed or future versions being
  accepted implicitly.
- **Exotic `$ref` lookalikes are ordinary input.** Inherited/accessor `$ref`
  properties, non-enumerable wrappers, and wrappers with hidden, symbol or extra
  keys are no longer recognized as references. Ordinary exact one-field
  wrappers are unchanged.
- **Stored-job execution is retired.** The repository endpoint
  `POST /api/jobs/:id/execute` returns 410; this is not a package-root API removal.
- **Client approval claims confer no authority.** Hosts must configure an
  authorizer and derive callers from authenticated host state.
- **HTTP requests are conservatively destructive.** Existing repository clients
  relying on default read authorization must explicitly allow the intended
  operation.
- **Shell invocation is exact.** Executable/argv prefix extensions, ambiguous
  encodings and unreviewed tuples are rejected. This is repository capability
  policy hardening, not an npm root export change.
- **V2 is opt-in and semantically different.** V2 rejects values outside its
  governed domain and removes shared container identity between source,
  authorization and outer capability entry. Test identity, mutation and rich
  object assumptions before enabling it.

Package version, capability versions and ExecutionPlan versions remain separate.
Installing v0.3.0 does not automatically select ExecutionPlan `2.0`.

## Public package surface

The package continues to expose only its root entry point. v0.3.0 adds public
admission diagnostic types and `isPlanAdmissionError` through that root and adds
`planVersions` to `OperatorRuntimeOptions`. It does not expose governed-value
helpers, admission issuers, registries, JobManager, stores, providers,
capabilities or validators as public subpaths.

## Research is not shipped functionality

Experiment I and the frozen 45-trial Experiment II record provide bounded
empirical evidence about external-model reasoning and the experiment harness.
They are repository research artifacts, are excluded from the npm package, and
are not runtime product guarantees. Release verification uses offline fixtures
and makes no live provider/model call.

The experiments do not establish a security proof, universal provider/model
reliability, hostile-code or hostile-process isolation, provider-operation or
external-effect equivalence, rollback, retry safety, exactly-once execution,
persistence parity, committed-result immutability, or passive/getter-safe/
Proxy-safe result traversal.

## Dependencies and starter security

Declared runtime dependency ranges are unchanged. The root lockfile refreshes
the resolved `zod` version from 4.5.4 to 4.6.5. Development and verification
tooling refreshes include Fastify 5.12.5, `tsx` 4.23.15, `@types/node` 26.6.2,
and `@babel/parser` 8.0.6 with its matching Babel helpers. Development-only
dependencies are not part of the npm runtime dependency graph.

The starter lockfile security remediation refreshes `fast-uri` 3.1.5 to 3.1.8,
Hono 4.13.2 to 4.13.9, and `qs` 6.15.3 to 6.16.0 without changing the starter's
declared application dependency ranges. The root, starter and starter-client
lockfiles are independently audited as release gates.

## Explicit trust-boundary limits

Installed capabilities, middleware and providers are executable in-process host
code, not hostile-plugin isolation subjects. Their trusted placement does not
make them authorization authorities. Live result getters and Proxy traps can run
during pre-capture result-path traversal; V2 governs the value returned by that
traversal, not traversal behavior itself.

Veil still does not promise committed-result stability, persistence/reload
parity, provider/effect equivalence, rollback, retries, exactly-once execution,
hostile-code isolation or deterministic external results. Plans remain linear;
DAGs, parallel execution, conditionals and cancellation are not implemented.
