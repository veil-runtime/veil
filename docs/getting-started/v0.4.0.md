# Veil Core v0.4.0 candidate

Status: **unpublished candidate** based on published v0.3.1. Core is deterministic
governed execution and evidence; it functions without any AI model or UI.
UI and Emergence evolve separately. Caretaker and autonomous repository-task
applications are not included in this candidate or its npm artifact.

The supported execution platform is **Linux** (qualified on x86_64/WSL2, Node 24).
**Windows and macOS are unqualified** and are outside this release qualification.

The Linux qualification passed 328 Core tests, 216 quality-harness tests, package
consumer checks and nine filesystem security regressions. The four flagged quality
controls were reviewed and accepted; the comparison still exits 1. See the
[committed qualification and review record](https://github.com/veil-runtime/veil/blob/903efad9c7212f1f1137407cf2401973577a5287/docs/release/v0.4.0-readiness.md).
This is verification evidence, not confirmation of npm publication.

## Changes

- The source-tree filesystem reader rejects final/parent symlinks, hard links and
  special files, bounds input to 200,000 bytes, and preserves the existing result
  shape and 50,000-code-unit output cap. Linux uses pinned directory descriptors;
  portable implementations require quiescent host directories. See
  [confinement and race limits](../architecture/filesystem-confinement.html).
- Fastify and transitive Hono are updated within compatible dependency ranges.
  Consumers must audit/refresh their own locks: a package upgrade alone does not
  force replacement of every previously locked transitive dependency.
  Dependency advisories and final audit results are recorded in the repository's
  `docs/release/v0.4.0-readiness.md`.
- The existing source-server local planner is experimental, opt-in and bounded. The default
  route is deterministic; local inference requires host opt-in and explicit
  selection. Generated plans still require runtime admission and authorization.
  See [local planning](../guides/local-planning.html).
- Tests clean generated test output before compilation. Package verification
  asserts the sole root entry and excludes other component/application trees.

## Compatibility

The [public exports](../reference/public-exports.html) are unchanged from v0.3.1.
V1 remains the default. V2 requires trusted-host `planVersions` configuration;
authorization views and detached invocation values retain their existing
semantics. Admission diagnostics, job/result/event contracts and reference
semantics are unchanged. No registry, provider, store or validator becomes public.

For source-server users: local models are no longer contacted by default.
Enable `OPERATOR_LOCAL_PLANNERS=1`, configure `QWEN_BASE_URL`/`QWEN_MODEL`, and
explicitly request `qwen-local`. The default endpoint is Ollama-compatible
`http://127.0.0.1:11434/v1`; the default Qwen model identifier is `qwen3:0.6b`.
Use an installed model's exact identifier. Remote HTTP endpoints now require
HTTPS; redirects and URL credentials/query/fragment are rejected. Local limits
may reject requests previously allowed to run without bounds.

Source filesystem users must remove symlink/hard-link dependencies and keep files
within the byte limit. These are deliberate security restrictions. Those built-in
capabilities and the local provider remain source-server facilities, not npm API.
Applications using npm implement the existing public `Planner` interface or
submit plans directly; deterministic execution has no inference dependency.

## Limits and verification

Core does not add cancellation, autonomous loops, general execution budgets,
sandbox isolation, tenant isolation, retries or exactly-once effects. Risk labels
do not authenticate callers. The local development HTTP server remains loopback
and unauthenticated. Registries/stores are process-global; use host boundaries
for separate tenants. See [trust boundaries](../architecture/trust-boundaries.html).

Offline planner tests establish transport bounds and governed execution of
generated proposals. They do not establish live model quality or a provider-side
token/billing guarantee. All nine Linux filesystem regressions pass, including
controlled path races and resource bounds. Jekyll output is validated under `/veil`
for local targets, fragments, navigation and layout structure. Windows/macOS remain
unqualified pending native execution and security testing. Local model planning
is experimental: failed write-planning probes are retained, and reliable autonomous
write planning is not claimed or required for deterministic Core qualification.

Install the candidate from a [locally verified tarball](installation.html).
Publication, release tagging and deployment are separate maintainer actions.
