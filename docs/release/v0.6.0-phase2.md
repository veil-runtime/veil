## Design and ownership

`OperatorRuntime` owns a supervision scope for an opted-in submission and
releases its host abort listener and deadline timer in `finally`. The scope uses
a monotonic deadline and a runtime-owned AbortController. The first observed
host abort or expiry fixes its failure reason. Stop clears the timer immediately.
Scheduling checkpoints also detect elapsed deadlines when synchronous code
delays timer dispatch. JavaScript cannot preempt a blocked event loop.

JobManager retains the existing admission, resolution, validation, authorization,
V2 copy-before-entry and sequential execution order. It supervises authorization
and capability waits through guarded operations. The wait installs its abort
listener before invoking foreign work and attaches both fulfillment and rejection
handlers, even when work aborts synchronously. A late response has no continuation
that can update Job/step results or events. Checkpoints before capability entry,
after capability response and before successful Job termination close the
completion/abort scheduling races. Invalid authorization still fails closed.

Logical terminal selection occurs synchronously before final persistence. A late
abort cannot turn a selected completion into cancellation. Existing persistence
failures can still reject the API call and use the existing failed-Job handling;
this phase does not redesign storage failure semantics. Runtime terminal-state
immutability concerns late supervised work and aborts, not freezing public Job
objects or changing existing storage/host mutation semantics.

Each execute invocation retains Phase 1's single lazy JobLogSink. For supervised
capabilities it also tracks the actual returned promise, separately from the
interruptible wait. Logical failure can return before that promise settles.
Cleanup then runs on either settlement, without changing Job state. A late
logger call before settlement can still write; after disposal it cannot reopen
SQLite. Pending authorization owns no capability logger. Cleanup throws are
diagnosed and contained, including deferred cleanup and persistence failure.
No shared store, provider or runtime instance is disposed.

## Transition and race table

Both semantic versions use the same supervision transitions. All execution stops
use existing `failed` Job status/outcome, `job.failed`, and fixed error strings
`Execution cancelled` or `Execution deadline exceeded`. No public union changes.

| State / trigger | Transition and scheduling decision | Late work / resource decision |
| --- | --- | --- |
| Invalid host timeout option | Reject configuration before submission work | No scope timer or Job |
| Pre-aborted signal + invalid plan | Existing admission rejection; no Job | Cancellation cannot admit an invalid plan |
| Pre-aborted signal + valid plan | Admit/create, then fail Job; all steps pending | No authorization or capability entry |
| Abort/expiry during admission or Job setup | Complete admission/setup, then stop at scheduling checkpoint | Storage is awaited, never raced against cancellation |
| Abort/expiry during resolved-input work | Fail current step when next checkpoint is reached | No authorization/capability entry after the stop is observed |
| Abort/expiry during authorization | Fail current step and Job; later steps pending | Late allow/deny/rejection is observed and discarded; no logger to retain |
| Explicit deny or malformed authorization | Existing denial/failed-step path; no capability entry | Supervision never grants authority |
| Abort from capability.started observer | Start event exists, then fail current step before actual invocation | Entry checkpoint prevents invocation |
| Abort/expiry during capability execution | Abort context signal; fail current step/Job; later steps pending | Retain logger until returned capability promise settles |
| Noncooperative late fulfillment | No result, event, status or scheduling update | Dispose logger on settlement |
| Noncooperative late rejection | Rejection handler observes it; terminal state unchanged | Dispose logger on settlement; no unhandled rejection |
| Abort plus capability response in the same turn | Observed stop wins before result commit | Returned value cannot revive Job |
| Response committed, then abort from capability.completed observer | Completed step/result retained; stop before next step or Job success | No rollback of completed effects |
| Abort and deadline both fire / repeated abort | First observed stop reason retained | At most one terminal Job failure; no duplicate scheduling |
| Job success already selected, then abort during persistence or after return | Completion remains selected | Host listener/timer removed when submission settles |
| Cleanup also throws | Preserve primary execution/cancellation/deadline or persistence failure | Bounded Phase 1 diagnostic; no rejected cleanup continuation |
| Returned capability promise never settles | Job may logically terminate; later steps never start | Logger ownership can remain indefinitely |

## API additions and compatibility

Existing exported `ExecutePlanOptions` and `RunJobOptions` gain optional
`signal?: AbortSignal` and `timeoutMs?: number`. Existing `ExecutionContext`
gains `readonly signal?: AbortSignal`. No new package-root exports are needed;
the supervision helper stays internal. No ExecutionPlan, Capability signature,
authorization, Job, result or event shapes change.

The timeout is an integer in `[0, 2147483647]` milliseconds, measured from entry
to `executePlan`, including admission/setup. Zero permits admission but prevents
capability entry. `run` plans normally and forwards supervision only to execution;
its planning time is outside this budget. These are trusted host options, never
instructions embedded in a plan, caller metadata or model output.

With neither option configured there is no supervision scope, extra signal
property or promise race. Caller capture, V1 shared-value behavior, V2 governed
capture/copy and result identity remain intact. Configured capabilities receive
a runtime-owned combined signal and must explicitly pass it to provider APIs.
Authorizers receive their existing context and cannot be forcibly interrupted.

## Limits and remaining Phase 3 work

Cancellation does not undo completed effects. A timeout is not evidence that an
external action did not occur. Noncooperative code may continue external work
after logical termination. Core prevents its late response from advancing runtime
state; it cannot forcibly stop JavaScript, isolate shared V1/V2 values, or prevent
arbitrary trusted same-process code from mutating objects it already holds.

The resource boundary is the returned capability promise. Detached background
work, including work hidden behind a middleware-local early-return timeout, is
not tracked. A capability must keep its returned promise pending for all work
using the logger. A permanently unsettled promise can retain resources forever;
force-disposal would violate ownership. Logging remains Phase 1 best effort,
without durability, drain or delivery guarantees. Persistence and planning are
not interruptible, and stored-job replay/concurrent execution are outside scope.
