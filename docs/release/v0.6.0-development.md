## Implemented guarantees

ExecutionPlan remains the reasoning/execution boundary; OperatorRuntime owns
execution authority. PlannerRouter selects a strategy, the strategy produces a
plan, and `run` submits it through the same `executePlan` admission path.
Registration and introspection do not grant authorization. Public Job/result/
event contracts, Capability and ExecutionPlan are unchanged by integration.

The execution order is:

1. Check and synchronously reserve configured instance capacity before reading
   the plan/caller or setting up supervision. Full capacity rejects immediately.
2. Set up requested supervision and capture caller identity; admit the enabled
   plan version. With `maxPlanSteps`, reject excessive array length before
   enumerating/copying steps, reading goal/key, validating input or creating a Job.
   Without this limit, preserve the legacy structural getter order.
3. Capture the structural envelope, validate the plan, create/persist the Job.
4. Before each step, checkpoint supervision, resolve references, capture V2
   values and validate resolved input. Await the configured authorizer and
   require an own, well-formed explicit `allow` decision. Deny, malformed
   decisions and exceptions prevent capability entry.
5. Create the detached V2 entry copy before the running/start transition;
   V1 retains shared input semantics. Check supervision before that transition
   and in the guarded invocation. Cancellation from a start-event observer
   therefore also prevents capability entry.
6. Observe actual authorization/capability work separately from interruptible
   waits. Check again before accepting results or advancing execution. Logical
   termination fails the Job and leaves later steps pending. Late settlement
   only releases ownership; it cannot update terminal Job/results/events.
7. Dispose this execution's lazy SQLite logging owner when actual capability
   work settles. Release capacity exactly once after submission/final persistence
   and all observed authorization/capability promises settle. Persistence failure
   does not free a slot while tracked work remains.

| Boundary | Guarantee and practical limit |
| --- | --- |
| Logical cancellation vs external termination | Cancellation stops runtime scheduling and signals cooperative capability code. It cannot forcibly terminate JavaScript, an authorizer or external effects. |
| Deadline vs rollback | `timeoutMs` starts at executePlan submission, excludes planning, and fails execution at guarded waits/checkpoints. It neither rolls back completed work nor proves an external effect did not occur. Persistence and synchronous code are not forcibly interrupted. |
| Instance capacity vs host capacity | `maxActiveExecutions` is per OperatorRuntime instance, rejects without queueing, and includes logically stopped but unsettled work. Other instances still admit independently; no tenant/process/provider-wide quota is implied. |
| Best-effort logging vs durable audit | Throws, rejections and serialization failures are contained; every composite sink is attempted. Entries can be lost, and diagnostics stop after ten attempts per loaded diagnostic module. No acknowledgement, drain, retry or delivery guarantee exists. |
| Internal ownership vs runtime disposal | Each execution owns one lazy SQLite logging connection; read queries own separate short-lived connections. Cleanup closes only owned handles. No public runtime shutdown, shared-service disposal or provider disposal API is added. |

Omitted limits remain unbounded. Limits accept nonnegative safe integers, including
zero. Planning runs outside the capacity reservation. A small step count does not
bound input bytes, nesting, getter/Proxy cost or result size. V2 remains opt-in;
neither capacity nor supervision changes V1/V2 value semantics. Without requested
supervision the capability context has no signal property.

objects it already holds. No retry, rollback, durable audit, host-wide admission,
idempotency enforcement, crash recovery or general runtime disposal is promised.
