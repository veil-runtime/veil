## Semantics and ownership

The requested additive `OperatorRuntimeOptions` are `maxPlanSteps?: number` and
`maxActiveExecutions?: number`. They are captured trusted host policy, independent
of model output, plan metadata, caller metadata and per-call options. Omission
means unbounded. Each configured value must be a nonnegative safe integer;
negative, fractional, nonfinite, unsafe and non-number values reject construction.
Zero is valid and blocks nonempty plans or all submissions, respectively.

After version admission, JobManager reads the submitted step-array length once
and rejects excess length before copying or traversing elements, reading plan
goal/key, validating inputs, creating Jobs, authorizing or invoking capabilities.
Holes count toward the length; oversized sparse arrays need no enumeration.
At or below the limit, existing validation applies, including empty-plan
diagnostics and sparse-plan rejection. A small step count does not bound input
size, nesting, reference traversal or synchronous getter/Proxy costs.

OperatorRuntime owns its reservation count. The full-capacity check and reserve
occur synchronously before plan/caller access and supervision setup, so concurrent
or reentrant submissions cannot take the same slot. Full submissions reject
immediately; there is no queue. Full capacity takes precedence over other
submission errors. `run` performs planning outside the reservation and forwards
its resulting plan through normal execution admission.

The runtime observes actual authorization and capability promises separately from
Phase 2's interruptible waits. The reservation releases exactly once, when both
the main submission (including final persistence) and all observed work settle.
Sync throws, fulfillment and rejection all release ownership. Pending work keeps
the slot after cancellation, deadline expiry or final persistence failure.
Reservations retain only a pending count, without accumulating settled results
or a per-step promise list. Phase 2 logger cleanup still follows actual capability
settlement. No shared resource is disposed by capacity accounting.

| Trigger | Job/entry behavior | Reservation behavior |
| --- | --- | --- |
| Invalid construction limit | Throw before any submission | No reservation |
| Full instance, including zero capacity | Reject; no Job/events/authorization/invocation | Existing reservations unchanged |
| Oversized valid-version plan | Reject; no Job/events/authorization/invocation | Temporary reservation releases on rejection |
| Invalid plan or timeout, throwing capture | Existing rejection | Release after submission settles |
| Pre-aborted valid plan with free capacity | Admit then fail Job, all steps pending | Release after persistence; no underlying work |
| Cancellation/expiry awaiting authorization | Fail Job; no capability entry | Retain until actual authorization settles |
| Cancellation/expiry during capability execution | Fail Job; later steps remain pending | Retain until actual capability settles |
| Cooperative provider stops and rejects | Failed Job; rejection observed | Recover after submission and work settle |
| Noncooperative late fulfillment/rejection | No late Job/result/event mutation | Recover on actual settlement |
| Repeated abort or completion/abort race | Phase 2 terminal arbitration retained | No double release |
| Underlying promise never settles | Logical failure can return | Slot can remain reserved indefinitely |

Limit rejections are ordinary Errors with fixed local messages `Execution plan
step limit exceeded` and `Active execution capacity exceeded`. They do not issue
ADR-0012 diagnostics or extend its public issue-code union. Existing Job/result/
event and authorization shapes remain unchanged. Capacity by itself adds no
context signal; supervision still requires explicit signal/timeout options.

## Compatibility, security and integration recommendation

ExecutionPlan remains the reasoning/execution boundary and OperatorRuntime still
governs all submissions. V1 shared inputs/results, V2 governed capture/copy,
authorization contexts/decisions and Job/result/event contracts remain intact.
New options extend the existing runtime policy; all tracking helpers stay internal.
Root exports and package boundaries are unchanged. Defaults remain unbounded,
with absent context signal unless supervision was explicitly requested. No retry,
idempotency enforcement, crash recovery or authority inferred from capacity.

Capacity is per instance, not per tenant/process/provider. Global registries,
Job storage, event bus and shared services still permit aggregate work from other
instances. Nonsettling authorizers/providers can hold slots indefinitely. A
returned promise cannot describe detached work or external effects that outlive
it. Cancellation/deadlines guarantee neither rollback nor termination of external
effects; synchronous work can still block the event loop. Hosts must select
limits and shared-service admission policy appropriate to their deployment.

Recommend integrating this implementation into the unified v0.6.0 development
line after maintainer review of the draft and explicit disposition of the five
final anchors plus inherited Phase 1 findings. Keep inventory equality and the
v0.5.0 comparator unchanged until any separately approved adoption action. The
functional gate is green; governance adoption and dependency advisory review
remain outstanding release work. Do not treat this as release approval or begin
publication/full cross-platform qualification from this phase.
