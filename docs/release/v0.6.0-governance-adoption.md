## Authorization, admission and execution boundaries

- **Authorization stays mandatory:** G3 is the sole changed runtime capability invocation. Registry resolution and resolved-input validation precede the authorizer; only an own, well-formed `allow` permits entry. Deny, malformed decisions, throwing accessors and authorizer rejection stop execution. Evidence: `test/execution-contract.test.ts:375,431,488,498,511,581,589` and integrated V1/V2 deny/malformed/throw cases at `test/execution-integration.test.ts:118`.
- **Same execution entrance:** G4 → G1 → G3 remains OperatorRuntime → admitted JobManager → authorized capability. G5 only obtains a plan. No new route/provider invocation, registration authority or replay entrance is introduced. Unchanged route regressions at `test/governance-routes.test.ts:76,113,166,197` verify host identity, admission and retired stored-job execution.
- **Cancellation/deadlines only restrict scheduling:** `ExecutionSupervision.wait` checkpoints before calling its operation and on actual settlement; stop never manufactures an authorization decision. Cancellation during authorization cannot turn a late allow into entry. A second wait checkpoint fences cancellation from the capability.started observer. Late results cannot schedule later steps or mutate terminal Jobs. Evidence: `test/execution-supervision.test.ts:40,62,89,141,161,173,358`; integrated races at `test/execution-integration.test.ts:45`.
- **Capacity cannot weaken validation:** captured trusted construction limits only reject; reserve is synchronous before caller/plan reads, with no await between check and increment. Max-plan length rejection precedes traversal; accepted sizes still follow the existing version, structural, schema and reference validators. Submission and actual work must both settle before release. Evidence: `test/execution-capacity.test.ts:60,75,85,135,166,213,248,271,287`.
- **V1/V2 semantics preserved:** no supervision/limits means existing defaults, V1 sharing and absent context.signal. V2 remains opt-in, captures before authorization, supplies frozen authorization input and detached entry input before running/start. No change to resolver, governed-value capture, validation or authorizer implementation. Evidence: `test/governed-value-v2.test.ts:41,56,106,181,268,275,297`, `test/execution-capacity.test.ts:258`, `test/execution-supervision.test.ts:321` and existing value-ownership tests. Supervision’s explicit options add the documented termination behavior; this is not a claim that opted-in termination leaves outcomes unchanged.
- **Dynamic authority unchanged:** new production dynamic sites use the fixed Symbol.dispose on locally constructed sink owners. T1 uses a literal logger-level list; T2–T4 use fixed symbols on local fixtures. Existing schema predicates, reflection, experiment metadata, SDK callbacks and private-import negative tests retain exact identities and their prior trust scope. No plan/caller field selects a newly privileged callable.
- **Package boundary intact:** root exports, package entry/exports/files metadata, SDK barrels, Capability, ExecutionPlan and public Job/step/event contracts are byte-unchanged from v0.5.0. Signal and host options extend existing interfaces; no new root export exposes internal supervision, tracking, stores, registries, providers or validators. The installed-package consumer and private-import rejection checks pass under `npm run check`.

These conclusions cover the reviewed delta and recognized scanner syntax, supported by behavioral tests. The scanner is not a transitive call-graph proof. Existing V1 input/result aliasing, pre-admission getters/Proxy effects, trusted host callbacks, globally shared registries/storage and SDK middleware behavior remain as documented. Cancellation does not guarantee external termination or rollback; never-settling work can retain capacity and logger handles. Those existing boundaries are not silently broadened into security guarantees.
