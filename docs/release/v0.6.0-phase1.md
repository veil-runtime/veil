# Core v0.6.0 Phase 1: runtime reliability

Status: implementation and local qualification complete; draft review only.
No merge or publication is authorized by this report.

## Scope and confirmed causes

Branch: `feat/core-v0.6.0-phase1-runtime-reliability`, created from freshly
HTTPS-fetched develop `7701e7b2bd4b4fe2f227be058951ef70bbbcc077`.
Implementation commit: `540d9ebcfe82b91f09a9789653e2ea14d377202b`.
Fixed quality comparison: `v0.5.0`, resolving to
`78713066cafba46b0c2f1cd40eed0e9937102002`.

Confirmed causes:

1. `ConsoleExecutionLogger.write` discarded the sink promise and did not guard
   synchronous throws. A rejected composite promise could outlive a successful Job.
2. `CompositeLogSink` called sinks in an unguarded map. A synchronous throw stopped
   later sinks from being attempted; rejecting sinks rejected the aggregate.
3. Console and SQLite JSON serialization can throw on cyclic metadata. The
   dispatch failures above let this become an unhandled rejection.
4. JobManager constructed a SQLite sink per authorized step, even without any
   log calls, with no disposal path. Schema initialization errors could strand
   an already opened connection.
5. The read-side singleton opened a database on module import and retained it
   without an explicit lifetime or disposal path.

## Architecture and ownership decisions

Logger dispatch guards both throws and promise rejections. Composite fan-out
guards each sink independently and attempts every destination. Serialization is
unchanged: invalid metadata may lose that log entry; it cannot fail the Job.
No metadata cloning, substitution, or changes to V1/V2 value semantics are added.

Diagnostics use a fixed string with no exception, metadata, identifiers or log
message. Output is limited to ten attempts per loaded diagnostic module per
process, with synchronous reentrancy protection. Diagnostic throws and rejected
promises are swallowed without further reporting. This is best effort logging,
with no durable audit guarantee, acknowledgement, retry, drain or delivery promise.

Each `JobManager.execute` invocation owns a lazy `JobLogSink`. Its first write
attempt constructs one SQLite sink; an unsuccessful construction is not retried
within the Job. SQLite writes run synchronously before sink dispatch returns.
JobManager's `finally` disposes only that invocation's sink on success or failure,
including failure while persisting the final Job. A capability retaining its logger
cannot reopen SQLite after the owner is disposed. Console logging can still be
attempted through that retained logger.

`Symbol.dispose` is an internal implementation detail on non-exported sink types,
not an OperatorRuntime or package-root lifecycle API. No public `close()` or
`drain()` was introduced. There is no global database handle to close and no
runtime instance may dispose another instance's logging connection. Concurrent
Jobs may independently connect to the same database file.

SQLite schema-construction failure disposes the just-created connection before
rethrowing the original error. Close failure is diagnosed and contained. If native
SQLite refuses close, release cannot be guaranteed; no retry or force-close is
invented. That case is explicitly tested with test-owned final cleanup.

`ExecutionLogStore` retains a path, opens a connection per `listByJob` query, and
closes it in `finally`, including query/JSON decoding failure. Importing the
singleton opens no connection. Existing query exceptions propagate; a cleanup
exception cannot replace them. No shared job store, event bus, registry, provider,
or OperatorRuntime resource is disposed here.

ExecutionPlan admission, OperatorRuntime authority, authorization order, public
Job/result/event contracts, exports and package dependencies are unchanged.

## Regression and lifecycle evidence

The fourteen regressions cover all logger levels; throwing, rejecting and hostile
thenable sinks; composite continuation; cyclic console/SQLite metadata; primary
execution errors; diagnostic recursion/throw/rejection/limits; construction/open
failure; construction rollback with failing cleanup; successful execution with
cleanup failure; native close refusal; concurrent runtimes; retained loggers;
idempotent internal disposal; and repeated read/write resource ownership.

The repeated-execution test measures 20 two-step Jobs and 80 log calls: exactly
20 distinct SQLite connections, all closed at each Job boundary. A silent Job
adds zero connections. The read-store test measures ten queries and one failed
query: eleven closes, while the separately owned writer stays open.

The exact installed tarball was also exercised through its public API from
`/tmp/veil-v060-phase1-consumer-685t9n6n`, outside the repository. Thirty Jobs with
60 steps alternate V1/V2, log cyclic metadata, and preserve successful results.
A further failed V2 Job preserves its primary error. Linux `/proc/self/fd`
measurement for the actual database path: before **0**, peak **1**, after **0**,
and back to zero after every Job. No unhandled rejection occurred.

## Remaining risks and Phase 2 recommendation

Logging remains best effort: invalid serialization, sink failure, process loss,
or writes from retained loggers after Job completion can lose SQLite log entries.
Async foreign sinks have rejection containment but no drain/durability guarantee.
The ten-attempt diagnostic budget suppresses later failures in a long-lived process.
A native close refusal can leave a handle live until native/process cleanup; the
runtime contains the error and makes no guarantee otherwise. Query-scoped reads
trade connection setup overhead for deterministic ownership. Shared services
outside logging have not been redesigned or disposed.

Qualification here is Linux only. Phase 2 should begin with maintainer review of
the exact governance inventory, repeat qualification on macOS/Windows, and resolve
the cached-consumer dependency warning under the existing dependency policy.
Measure logging under concurrent load before considering any performance change.
Any stronger audit delivery, asynchronous draining, or public lifecycle contract
needs a separate compatibility and shared-ownership decision. No automatic retry
or idempotency policy is part of this phase.
