## Security remediation and limits

`src/providers/filesystem/confined-file-reader.ts` replaces lexical-only reads
in `src/capabilities/filesystem/file-read.ts`. It rejects final/parent/internal
symlinks, hard links, special files and files above 200,000 bytes. Reads use a
fixed 200,001-byte buffer and retain the existing 50,000-code-unit result limit.
Linux uses pinned directory descriptors, no-follow/nonblocking opens and opened
file containment checks. Portable checks require quiescent host directories;
there is no claim of portable race-free confinement, transactional file snapshots,
hostile mount protection, general IO cancellation or aggregate process quotas.
See `docs/architecture/filesystem-confinement.md` for the exact threat boundary.

The nine Linux filesystem tests include the original governed V1/V2 symlink
exploit, zero-open policy denial, links, FIFO/socket rejection, parent replacement,
final symlink swap, bounded growth and portable identity-check behavior simulated
on Linux. Simulation is not execution on macOS/Windows. The new CI matrix requires
actual Ubuntu/macOS/Windows hosts and does not skip common security cases.

Root dependency changes: Fastify 5.12.5 -> 5.12.7 and Hono 4.13.7 -> 4.13.13;
MCP SDK remains 1.32.1. Hono is transitive through MCP SDK, while Fastify is a
development dependency used by the source server/tests. No Veil use of the
affected Hono `serveStatic` or Fastify header `propertyNames` feature was found.
The fixes stay within compatible ranges; no suppression/override was introduced.
The Hono change is in the candidate lockfile. Root runtime dependency ranges are
unchanged; downstream package consumers must audit/refresh their own locks, since
upgrading Core alone need not replace an already locked transitive dependency.
Advisories: [Hono](https://github.com/advisories/GHSA-5r4p-p66f-jhc7),
[Fastify](https://github.com/advisories/GHSA-389g-gv7q-r4x8).

The Starter server's independent MCP lock also needed compatible Hono,
`ip-address` and `proxy-addr` updates. Its direct SDK range is aligned to ^1.32.1.
Root full/production audits and the final Starter server audit report zero
vulnerabilities. The unchanged separate Starter client builds but reports two
high advisory entries (`vite` 8.2.1 and `source-map-js` 1.2.1). That UI dependency
work is outside this Core assignment and is not shipped in the Core tarball.

## Core and roadmap assessment

The accepted roadmap's constrained local Qwen planner already existed internally.
The candidate hardens it rather than adding an autonomous subsystem or public
provider API. `OPERATOR_LOCAL_PLANNERS=1` enables source-server registration;
explicit planner/strategy selection is required. Default routing is deterministic.
Generation/health calls have deadlines and request/streamed response caps;
the request limits output tokens and the adapter bounds steps. Unknown capabilities,
authority fields, malformed/truncated output and invalid configurations fail.
Version-pinned V1 plans then pass existing admission and host authorization.

The public package still supports application-owned `Planner` implementations and
direct plans, without model startup or inference dependencies. The local provider
and built-in capabilities remain source-tree facilities, not npm exports.

The public exports, ExecutionPlan/Capability/OperatorRuntime contracts, job/result/
event contracts, authorizer, admission/resolution machinery, registry, event bus,
V1/V2 ownership implementation and accepted ADRs are unchanged from v0.3.1.
Existing regressions cover discovery, malformed/denied authorization, V1/V2,
references, lifecycle and MCP/HTTP entrances. The new integration tests additionally
prove generated writes remain denied and missing/wrong inputs reach neither
authorization nor invocation. No new cancellation, budget or tenant isolation
guarantee is introduced. Registries, job memory and stores remain process-global;
host credentials, authentication, concurrency and tenant separation are host-owned.
The source browser capability still permits HTTP/HTTPS destinations without an
SSRF/private-address/redirect isolation policy. The bundled server is a trusted
loopback development host, not a remotely deployable authenticated service.
Hosts exposing browser/HTTP capabilities must separately constrain network access,
credentials and destinations; read-risk permission alone does not establish that.

### Local inference observations

`ollama list` found existing `qwen3:0.6b` (model ID prefix `7df6b6e09427`). A
bounded live smoke used only synthetic `fixture.echo`/`fixture.write` capabilities,
no repository data or paid API. Initial output omitted a required field and was
rejected by runtime admission before execution. After clarifying field-map
instructions, another read completed but included punctuation in the value; a
write proposal was invalid JSON. The final exact-value read completed in 5,340 ms
and returned `{ "value": "core-v0.4-smoke" }`. The final write-planning call timed
out at the configured 30 seconds, with no write execution. The combined final
smoke exits 1, not green. Automated opt-in/runtime tests separately prove a valid
model-proposed write is denied. No automatic retry was added.

These observations establish a working local read path and fail-closed rejection/
timeout, not reliable model reasoning or broad task success. The official
[Ollama compatibility reference](https://docs.ollama.com/api/openai-compatibility)
documents the endpoint protocol; model quality and provider-side accounting are
not Core guarantees. Live failures are preserved alongside success evidence.
